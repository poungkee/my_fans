## 배포 전략 비교

### Rolling Update (현재 사용 중)

**개념**: Kubernetes의 기본 배포 방식으로, 구버전 Pod를 하나씩 종료하며 신버전 Pod로 순차적으로 교체

```
시작:  [V1] [V1] [V1] [V1]  ← 100% 구버전
        │
Step 1: [V1] [V1] [V1] [V2]  ← V2 시작, V1 하나 종료
        │
Step 2: [V1] [V1] [V2] [V2]  ← 점진적 교체
        │
Step 3: [V1] [V2] [V2] [V2]
        │
완료:   [V2] [V2] [V2] [V2]  ← 100% 신버전

⏱️ 소요 시간: 5-10분
💰 추가 비용: ~0% (maxSurge 1개만)
```

#### 장점
- ✅ 추가 리소스 거의 불필요 (비용 최소)
- ✅ Kubernetes 기본 기능 (별도 도구 불필요)
- ✅ 설정 간단 (YAML 몇 줄)

#### 단점
- ❌ 롤백 느림 (5-10분)
- ❌ 50% 사용자가 버그 경험 가능
- ❌ 트래픽 비율 조절 불가

#### 현재 설정

```yaml
# environments/eks/manifests/04-main-api.yaml
spec:
  replicas: 2
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1        # 최대 1개 추가 Pod
      maxUnavailable: 0  # 무중단 배포
```

### Canary Deployment

**개념**: 신버전을 소수 사용자에게 먼저 노출하고, 메트릭을 확인하며 점진적으로 확대

```
시작:  [V1] [V1] [V1] [V1]  ← 100% V1 트래픽
        │
Step 1: [V1] [V1] [V1] [V1] [V2]
        └────80%────┘       └20%┘  ← 20% 사용자만 V2
        ⏱️ 5분 대기 + 메트릭 확인
        │
Step 2: [V1] [V1] [V2] [V2]
        └─50%─┘  └─50%─┘  ← 50% vs 50%
        ⏱️ 5분 대기 + 메트릭 확인
        │
Step 3: [V1] [V2] [V2] [V2]
        └25%┘ └───75%───┘  ← 75% V2로 확대
        ⏱️ 5분 대기 + 메트릭 확인
        │
완료:   [V2] [V2] [V2] [V2]  ← 100% V2

⏱️ 소요 시간: 20-30분 (안전하게)
💰 추가 비용: +3% (배포 중 추가 Pod)
```

#### 장점
- ✅ 점진적 노출 (20% → 50% → 100%)
- ✅ 자동 롤백 (Prometheus 메트릭 기반)
- ✅ 리스크 최소화 (소수 사용자만 영향)
- ✅ A/B 테스트 가능

#### 단점
- ❌ Argo Rollouts 학습 필요
- ❌ Prometheus 메트릭 필수
- ❌ 배포 시간 길어짐 (20-30분)

#### 구현 방법 (Argo Rollouts)

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: main-api
spec:
  replicas: 4
  strategy:
    canary:
      steps:
      - setWeight: 20
      - pause: {duration: 5m}
      - setWeight: 50
      - pause: {duration: 5m}
      - setWeight: 75
      - pause: {duration: 5m}
      analysis:
        templates:
        - templateName: success-rate
        args:
        - name: service-name
          value: main-api
---
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: success-rate
spec:
  metrics:
  - name: success-rate
    interval: 1m
    successCondition: result >= 0.95
    failureLimit: 2
    provider:
      prometheus:
        address: http://prometheus:9090
        query: |
          sum(rate(http_requests_total{status=~"2..",service="{{args.service-name}}"}[5m]))
          /
          sum(rate(http_requests_total{service="{{args.service-name}}"}[5m]))
```

### Blue/Green Deployment

**개념**: 신버전 환경(Green)을 완전히 구축한 후, 트래픽을 즉시 전환

```
Step 1: Blue 환경 (현재)
        [V1] [V1] [V1] [V1]  ← 100% 프로덕션 트래픽

        Green 환경 (신규 배포)
        [V2] [V2] [V2] [V2]  ← 0% 트래픽 (대기)

        ⏱️ Green 테스트 중...
        curl http://main-api-preview:3000

Step 2: 트래픽 전환 (즉시)
        [V1] [V1] [V1] [V1]  ← 0% 트래픽 (대기)
        [V2] [V2] [V2] [V2]  ← 100% 트래픽 ✅

        문제 발생 시? → 1초 만에 Blue로 복귀!

Step 3: Blue 삭제 (5분 후)
        [V2] [V2] [V2] [V2]  ← 100% 트래픽

⏱️ 전환 시간: 1초 (즉시)
💰 추가 비용: +20% (리소스 2배)
```

#### 장점
- ✅ 즉시 롤백 (1초)
- ✅ 완전한 테스트 후 전환
- ✅ 위험 최소화
- ✅ 예측 가능한 배포

#### 단점
- ❌ 리소스 2배 필요 (비용 증가)
- ❌ DB 마이그레이션 복잡
- ❌ 배포 중 리소스 낭비

#### 구현 방법 (Kubernetes)

```yaml
# Blue (현재 버전)
apiVersion: v1
kind: Service
metadata:
  name: main-api
spec:
  selector:
    app: main-api
    version: blue  # Blue 환경 선택
  ports:
  - port: 3000
---
# Green (신규 버전) 배포 후 테스트
apiVersion: v1
kind: Service
metadata:
  name: main-api-preview
spec:
  selector:
    app: main-api
    version: green  # Green 환경 선택
  ports:
  - port: 3000
---
# 전환: selector의 version만 변경
# blue → green 으로 즉시 전환
```

```sql
    'base64'

  );
```

```sql
  RETURN NULL;
END;
```

```bash
aws s3 cp backup_$(date +%Y%m%d).dump \
  s3://fans-backups/db/

# 3. 자동화 (CronJob)
apiVersion: batch/v1
kind: CronJob
metadata:
  name: db-backup
spec:
  schedule: "0 2 * * *"  # 매일 새벽 2시
  jobTemplate:
    spec:
      template:
        spec:
          containers:
          - name: backup
            image: postgres:15
            command:
            - /bin/sh
            - -c
            - |
              pg_dump -h $DB_HOST -U $DB_USERNAME \
                -d $DB_DATABASE \
                -F c -b -v -f /backup/backup_$(date +%Y%m%d).dump
              aws s3 cp /backup/backup_$(date +%Y%m%d).dump \
                s3://fans-backups/db/
          restartPolicy: OnFailure
```

**복구 절차**:

```bash
# 1. 백업 다운로드
aws s3 cp s3://fans-backups/db/backup_20251029.dump .

# 2. 데이터베이스 복원
pg_restore -h $DB_HOST -U $DB_USERNAME \
  -d $DB_DATABASE \
  -c -v backup_20251029.dump

# 3. 서비스 재시작
kubectl rollout restart deployment/main-api
```

**RTO (Recovery Time Objective)**: 1시간
**RPO (Recovery Point Objective)**: 24시간 (일 1회 백업)

### FAQ (자주 묻는 질문)

#### Q1: 로컬 환경 실행 시 메모리 부족 에러가 발생해요.

**A**: Docker Desktop 메모리 할당을 4GB 이상으로 증가시키세요.

```
Docker Desktop → Settings → Resources → Memory → 4GB 이상
```

---

#### Q2: AI 요약이 너무 느려요.

**A**: 배치 처리 크기를 줄이거나, GPU 인스턴스를 사용하세요.

```python
# backend/ai/summarize-ai/ai_module.py
MAX_BATCH_SIZE = 5  # 10 → 5로 감소
```

---

#### Q3: EKS 배포 시 ImagePullBackOff 에러가 나요.

**A**: ECR 권한 확인 및 IRSA 설정이 필요합니다.

```bash
# ECR 로그인 확인
aws ecr get-login-password --region ap-northeast-2

# IRSA 설정 확인
kubectl describe serviceaccount main-api -n default
```

---

#### Q4: 개발/운영 환경을 어떻게 구분하나요?

**A**: `DB_SCHEMA` 환경변수로 구분합니다.

```bash
# 로컬 개발
DB_SCHEMA=development

# 운영 환경
DB_SCHEMA=production
```

---

#### Q5: 배포 전략은 언제 변경해야 하나요?

**A**: 트래픽이 일 10만 이상일 때 Canary로 전환을 권장합니다.

```
현재: Rolling Update (일 1만 미만)
→ Canary (일 10만+)
→ Blue/Green (미션 크리티컬)
```
