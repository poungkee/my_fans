## 배포 전략 개요

무중단 배포는 서비스 중단 없이 새 버전을 배포하는 방법입니다. FANS 프로젝트에서는 Kubernetes를 사용하여 세 가지 주요 배포 전략을 지원합니다.

### 배포 전략 선택 기준

```
                    배포 전략 선택
                         │
                         ▼
              ┌──────────────────────┐
              │  트래픽 규모는?       │
              └──────────────────────┘
                         │
        ┌────────────────┼────────────────┐
        │                │                │
      <1만/일         1-10만/일        >10만/일
        │                │                │
        ▼                ▼                ▼
   Rolling Update      Canary      ┌──────────────┐
                                   │미션 크리티컬?│
                                   └──────────────┘
                                          │
                                    ┌─────┴─────┐
                                    │           │
                                   Yes         No
                                    │           │
                                    ▼           ▼
                              Blue/Green     Canary
```

## Rolling Update (현재 사용)

### 개념

Kubernetes의 기본 배포 방식으로, 구버전 Pod를 하나씩 종료하며 신버전 Pod로 순차적으로 교체합니다.

### 배포 과정

```
시작:  [V1] [V1] [V1] [V1]  ← 100% 구버전
        │
Step 1: [V1] [V1] [V1] [V2]  ← V2 시작, V1 하나 종료
        │
Step 2: [V1] [V1] [V2] [V2]  ← 점진적 교체
        │
Step 3: [V1] [V2] [V2] [V2]
        │
완료:   [V2] [V2] [V2] [V2]  ← 100% 신버전

⏱️ 소요 시간: 5-10분
💰 추가 비용: ~0% (maxSurge 1개만)
```

### 장점

- ✅ **추가 리소스 거의 불필요** - 비용 최소화
- ✅ **Kubernetes 기본 기능** - 별도 도구 불필요
- ✅ **설정 간단** - YAML 몇 줄로 구현

### 단점

- ❌ **롤백 느림** - 5-10분 소요
- ❌ **50% 사용자가 버그 경험 가능** - 점진적 교체 중 구버전과 신버전이 혼재
- ❌ **트래픽 비율 조절 불가** - Pod 수에 따라 자동 결정

### 현재 설정

```yaml
# environments/eks/manifests/04-main-api.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: main-api
spec:
  replicas: 2
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1        # 최대 1개 추가 Pod (총 3개까지)
      maxUnavailable: 0  # 무중단 배포 (최소 2개 유지)
```

### 사용 시나리오

**✅ 적합한 경우**:
- MVP / 베타 단계
- 트래픽이 적음 (일 1만 미만)
- 빠른 반복 개발 중
- 비용 최소화가 우선

**❌ 부적합한 경우**:
- 트래픽이 많음 (일 10만 이상)
- 미션 크리티컬한 서비스
- 배포 실패 시 영향 범위가 큼

## Canary Deployment

### 개념

신버전을 소수 사용자에게 먼저 노출하고, 메트릭을 확인하며 점진적으로 트래픽 비율을 확대하는 방식입니다.

### 배포 과정

```
시작:  [V1] [V1] [V1] [V1]  ← 100% V1 트래픽
        │
Step 1: [V1] [V1] [V1] [V1] [V2]
        └────80%────┘       └20%┘  ← 20% 사용자만 V2
        ⏱️ 5분 대기 + 메트릭 확인
        │
Step 2: [V1] [V1] [V2] [V2]
        └─50%─┘  └─50%─┘  ← 50% vs 50%
        ⏱️ 5분 대기 + 메트릭 확인
        │
Step 3: [V1] [V2] [V2] [V2]
        └25%┘ └───75%───┘  ← 75% V2로 확대
        ⏱️ 5분 대기 + 메트릭 확인
        │
완료:   [V2] [V2] [V2] [V2]  ← 100% V2

⏱️ 소요 시간: 20-30분 (안전하게)
💰 추가 비용: +3% (배포 중 추가 Pod)
```

### 장점

- ✅ **점진적 노출** - 20% → 50% → 100% 단계별 전환
- ✅ **자동 롤백** - Prometheus 메트릭 기반 실패 감지
- ✅ **리스크 최소화** - 소수 사용자만 영향 받음
- ✅ **A/B 테스트 가능** - 두 버전 동시 운영하며 비교

### 단점

- ❌ **Argo Rollouts 학습 필요** - 추가 도구 학습 곡선
- ❌ **Prometheus 메트릭 필수** - 모니터링 인프라 구축 필요
- ❌ **배포 시간 길어짐** - 20-30분 소요

### 구현 방법 (Argo Rollouts)

**1. Argo Rollouts 설치**

```bash
kubectl create namespace argo-rollouts
kubectl apply -n argo-rollouts -f https://github.com/argoproj/argo-rollouts/releases/latest/download/install.yaml
```

**2. Rollout 정의**

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: main-api
spec:
  replicas: 4
  strategy:
    canary:
      steps:
      - setWeight: 20      # 20% 트래픽
      - pause: {duration: 5m}
      - setWeight: 50      # 50% 트래픽
      - pause: {duration: 5m}
      - setWeight: 75      # 75% 트래픽
      - pause: {duration: 5m}
      analysis:
        templates:
        - templateName: success-rate
        args:
        - name: service-name
          value: main-api
  selector:
    matchLabels:
      app: main-api
  template:
    metadata:
      labels:
        app: main-api
    spec:
      containers:
      - name: main-api
        image: your-ecr-url/main-api:latest
        ports:
        - containerPort: 3000
```

**3. AnalysisTemplate 정의**

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: success-rate
spec:
  metrics:
  - name: success-rate
    interval: 1m
    successCondition: result >= 0.95  # 95% 성공률 이상
    failureLimit: 2  # 2회 실패 시 자동 롤백
    provider:
      prometheus:
        address: http://prometheus:9090
        query: |
          sum(rate(http_requests_total{status=~"2..",service="{{args.service-name}}"}[5m]))
          /
          sum(rate(http_requests_total{service="{{args.service-name}}"}[5m]))
```

**4. 배포 명령**

```bash
# Rollout 생성
kubectl apply -f rollout.yaml

# 배포 상태 확인
kubectl argo rollouts get rollout main-api --watch

# 수동으로 다음 단계 진행
kubectl argo rollouts promote main-api

# 롤백
kubectl argo rollouts abort main-api
kubectl argo rollouts undo main-api
```

### 사용 시나리오

**✅ 적합한 경우**:
- 정식 런칭 이후
- 트래픽 증가 (일 1-10만)
- 안정성 중요도 증가
- 배포 리스크 감소 필요

**❌ 부적합한 경우**:
- 모니터링 인프라 미구축
- 빠른 배포가 필요한 경우
- 팀 규모가 작아 복잡도 감당 어려움

## Blue/Green Deployment

### 개념

신버전 환경(Green)을 완전히 구축한 후, 트래픽을 즉시 전환하는 방식입니다.

### 배포 과정

```
Step 1: Blue 환경 (현재)
        [V1] [V1] [V1] [V1]  ← 100% 프로덕션 트래픽

        Green 환경 (신규 배포)
        [V2] [V2] [V2] [V2]  ← 0% 트래픽 (대기)

        ⏱️ Green 테스트 중...
        curl http://main-api-preview:3000

Step 2: 트래픽 전환 (즉시)
        [V1] [V1] [V1] [V1]  ← 0% 트래픽 (대기)
        [V2] [V2] [V2] [V2]  ← 100% 트래픽 ✅

        문제 발생 시? → 1초 만에 Blue로 복귀!

Step 3: Blue 삭제 (5분 후)
        [V2] [V2] [V2] [V2]  ← 100% 트래픽

⏱️ 전환 시간: 1초 (즉시)
💰 추가 비용: +20% (리소스 2배)
```

### 장점

- ✅ **즉시 롤백** - 1초 만에 복구 가능
- ✅ **완전한 테스트 후 전환** - 프로덕션과 동일한 환경에서 테스트
- ✅ **위험 최소화** - 검증된 환경으로 전환
- ✅ **예측 가능한 배포** - 트래픽 전환 시점 명확

### 단점

- ❌ **리소스 2배 필요** - 배포 중 두 환경 동시 운영
- ❌ **DB 마이그레이션 복잡** - 두 버전이 동일 DB 사용 시 호환성 문제
- ❌ **배포 중 리소스 낭비** - 잠깐 동안 Green 환경 유휴 상태

### 구현 방법 (Kubernetes)

**1. Blue 환경 (현재 버전)**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: main-api-blue
  labels:
    version: blue
spec:
  replicas: 2
  selector:
    matchLabels:
      app: main-api
      version: blue
  template:
    metadata:
      labels:
        app: main-api
        version: blue
    spec:
      containers:
      - name: main-api
        image: your-ecr-url/main-api:v1.0.0
        ports:
        - containerPort: 3000
---
apiVersion: v1
kind: Service
metadata:
  name: main-api
spec:
  selector:
    app: main-api
    version: blue  # Blue 환경 선택
  ports:
  - port: 3000
    targetPort: 3000
```

**2. Green 환경 배포 (신규 버전)**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: main-api-green
  labels:
    version: green
spec:
  replicas: 2
  selector:
    matchLabels:
      app: main-api
      version: green
  template:
    metadata:
      labels:
        app: main-api
        version: green
    spec:
      containers:
      - name: main-api
        image: your-ecr-url/main-api:v1.1.0
        ports:
        - containerPort: 3000
---
# 테스트용 Service
apiVersion: v1
kind: Service
metadata:
  name: main-api-preview
spec:
  selector:
    app: main-api
    version: green  # Green 환경 선택
  ports:
  - port: 3000
    targetPort: 3000
```

**3. 트래픽 전환 (Blue → Green)**

```bash
# Green 환경 테스트
curl http://main-api-preview:3000/health

# 트래픽 전환 (Service selector만 변경)
kubectl patch service main-api -p '{"spec":{"selector":{"version":"green"}}}'

# 전환 확인
kubectl get endpoints main-api

# 문제 발생 시 즉시 롤백
kubectl patch service main-api -p '{"spec":{"selector":{"version":"blue"}}}'
```

**4. Blue 환경 정리 (전환 후 5분 대기)**

```bash
kubectl delete deployment main-api-blue
```

### 사용 시나리오

**✅ 적합한 경우**:
- 미션 크리티컬한 서비스
- 트래픽이 매우 많음 (일 10만 이상)
- 즉시 롤백 필요
- 충분한 리소스 확보 가능

**❌ 부적합한 경우**:
- 비용 제약이 큼
- DB 마이그레이션이 복잡
- 빠른 배포가 필요한 경우

## 배포 전략 비교

### 비교표

| 항목 | Rolling Update | Canary | Blue/Green |
|:---:|:---:|:---:|:---:|
| **다운타임** | 없음 ✅ | 없음 ✅ | 없음 ✅ |
| **롤백 속도** | 5-10분 🐌 | 1분 🚀 | 즉시 ⚡ |
| **추가 비용** | **0%** | **+3%** | **+20%** |
| **구현 난이도** | ⭐ 쉬움 | ⭐⭐ 중간 | ⭐ 쉬움 |
| **트래픽 제어** | ❌ 불가 | ✅ 세밀함 | ⚠️ 전체만 |
| **리스크** | 🔴 높음 | 🟡 낮음 | 🟢 매우 낮음 |
| **필요 도구** | kubectl | Argo Rollouts | kubectl |
| **모니터링 필수** | ❌ | ✅ | ❌ |
| **A/B 테스트** | ❌ | ✅ | ❌ |

### ROI 분석

**Canary Deployment 도입 시**:
- 초기 투자: 1주일 (학습 + 구현)
- 추가 비용: +3% ($2/월)
- 효과: 배포 리스크 80% 감소, 장애 영향 범위 95% 감소
- ROI: 5,000% 이상

**Blue/Green Deployment 도입 시**:
- 초기 투자: 2일 (구현)
- 추가 비용: +20% ($12/월)
- 효과: 즉시 롤백, 완벽한 테스트 환경
- ROI: 미션 크리티컬 서비스에서 무한대

│ 이유:                                                    │
│   ✅ 트래픽 적음 (일 1만 미만)                          │
│   ✅ 빠른 반복 개발 중                                  │
│   ✅ 비용 최소화 우선                                   │
└─────────────────────────────────────────────────────────┘
                         │
                         ▼

│                                                          │
│ 구현 기간: 1주일                                         │

└─────────────────────────────────────────────────────────┘
                         │
                         ▼
┌─────────────────────────────────────────────────────────┐
│ Phase 3: 스케일업 (1년+)                                │
├─────────────────────────────────────────────────────────┤

### 전환 시점 체크리스트

#### Canary Deployment 도입 시점

- [ ] 일 트래픽 1만 이상
- [ ] Prometheus + Grafana 구축 완료
- [ ] 팀원 Kubernetes 숙련도 향상
- [ ] 배포 실패 시 영향 범위 증가
- [ ] 안정성 요구사항 증가

#### Blue/Green Deployment 도입 시점

- [ ] 일 트래픽 10만 이상
- [ ] 미션 크리티컬 기능 추가 (결제 등)
- [ ] 즉시 롤백 필요성 증가
- [ ] 리소스 2배 비용 감당 가능
- [ ] DB 마이그레이션 전략 수립 완료
