## 리소스 Right-Sizing

### 개념

리소스 Right-Sizing은 애플리케이션의 **실제 사용량**에 맞춰 요청량(requests)과 한계값(limits)을 설정하는 전략입니다.

### 비용 절감 효과

```
과도한 리소스 할당 (Before):
┌──────────────────────────────────┐
│ Requests: 1000m CPU + 2Gi Memory │  ← 실제 사용: 200m + 512Mi
│ Limits: 2000m CPU + 4Gi Memory   │  ← 실제 피크: 400m + 800Mi
└──────────────────────────────────┘
결과: 자원 낭비, 월 비용 $80

최적화 된 할당 (After):
┌──────────────────────────────────┐
│ Requests: 200m CPU + 512Mi Memory│  ← 실제 평균 사용량
│ Limits: 500m CPU + 1Gi Memory    │  ← 실제 피크 사용량
└──────────────────────────────────┘
결과: 효율적 사용, 월 비용 $20

절감율: 75%
```

### 구현 가이드

#### 1단계: 실제 사용량 분석


## Spot Instance 활용

### 개념

**Spot Instance**: AWS 여유 용량을 70% 할인된 가격에 제공하는 서비스
- 일반 On-Demand 인스턴스: $0.096/시간 (t3.medium)
- Spot 인스턴스: $0.029/시간 (70% 할인)
- 대신 언제든 종료될 수 있음 (보통 5분 전 알림)

### 적용 범위

```
✅ Spot Instance 적합:
├─ 배치 작업 (크롤러, 데이터 처리)
├─ 스케줄러 (정기적 실행 가능)
├─ 개발/테스트 환경
└─ 비상태 서비스 (재시작 가능)

❌ Spot Instance 부적합:
├─ API 서버 (지속적 가용성 필요)
├─ DB (데이터 손실 위험)
├─ 캐시 (상태 저장)
└─ 결제 처리 서비스 (안정성 필수)
```

### 구현 가이드

#### 1단계: Spot Node Group 생성

**Terraform 코드** (`environments/eks/terraform/eks.tf`):

```hcl
resource "aws_eks_node_group" "spot" {
  cluster_name    = aws_eks_cluster.main.name
  node_group_name = "fans-spot"
  node_role_arn   = aws_iam_role.eks_nodes.arn
  subnet_ids      = aws_subnet.private[*].id

  # Spot Instance 설정
  capacity_type  = "SPOT"                         # Spot 사용
  instance_types = ["t3.medium", "t3a.medium"]   # 여러 타입 (재시작 대비)

  # 스케일링 설정
  scaling_config {
    desired_size = 2    # 정상 상태
    max_size     = 4    # 최대 4개
    min_size     = 1    # 최소 1개
  }

  # 레이블 지정
  labels = {
    workload = "batch"
    capacity = "spot"
  }

  tags = {
    Name    = "FANS Spot Nodes"
    Purpose = "Batch Jobs"
  }
}
```

#### 2단계: Deployment에 Node Affinity 설정

**배치 작업 배포** (`environments/eks/manifests/10-scheduler.yaml`):

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: scheduler
  namespace: default
spec:
  replicas: 1
  selector:
    matchLabels:
      app: scheduler
  template:
    metadata:
      labels:
        app: scheduler
    spec:
      # Node 선택: Spot Instance 전용
      nodeSelector:
        workload: batch

      # 모든 노드 타입 허용 (t3.medium, t3a.medium)
      affinity:
        nodeAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 100
            preference:
              matchExpressions:
              - key: karpenter.sh/capacity-type
                operator: In
                values: ["spot"]

      # Spot 노드 종료 대비 Grace Period
      terminationGracePeriodSeconds: 30

      containers:
      - name: scheduler
        image: fans-scheduler:latest
        resources:
          requests:
            cpu: 100m
            memory: 256Mi
          limits:
            cpu: 300m
            memory: 512Mi
```

#### 3단계: Pod Disruption Budget 설정

크롤러가 Spot 노드 종료 시 신속하게 재시작되도록 설정:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: scheduler-pdb
spec:
  minAvailable: 1  # 최소 1개는 실행 중 유지
  selector:
    matchLabels:
      app: scheduler
```

## 스케일링 전략

### 1. 수평 확장 (Horizontal Pod Autoscaler - HPA)

#### 개념

HPA는 CPU/메모리 사용률이 설정된 임계값을 초과할 때 자동으로 Pod 개수를 증가시킵니다.

```
트래픽 증가:
┌────────────────────────────────────┐
│ 초기: 2 Pod (CPU 50% 사용)          │
├────────────────────────────────────┤
│ 트래픽 2배 증가                      │
│ → CPU 100% 도달                     │
│ → HPA 감지                          │
│ → 자동으로 Pod 3개 추가             │
│ → 최종: 5 Pod (CPU 40% 사용)        │
└────────────────────────────────────┘
```

#### CPU/Memory 기반 HPA

**Kubernetes 매니페스트** (`environments/eks/manifests/11-hpa.yaml`):

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: main-api-hpa
  namespace: default
spec:
  # 대상 Deployment
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: main-api

  # Pod 개수 범위
  minReplicas: 2   # 최소 2개 (고가용성)
  maxReplicas: 10  # 최대 10개 (비용 제어)

  # 스케일링 메트릭
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70  # CPU 70% 도달 시 스케일 아웃

  - type: Resource
    resource:
      name: memory
      target:
        type: Utilization
        averageUtilization: 80  # 메모리 80% 도달 시 스케일 아웃

  # 스케일링 동작 제어
  behavior:
    # 스케일 다운 (Pod 감소)
    scaleDown:
      stabilizationWindowSeconds: 300  # 5분 안정화 대기
      policies:
      - type: Percent
        value: 50              # 한 번에 50%만 축소
        periodSeconds: 60      # 1분마다 확인

    # 스케일 업 (Pod 증가)
    scaleUp:
      stabilizationWindowSeconds: 0    # 즉시 확장
      policies:
      - type: Percent
        value: 100             # 한 번에 2배까지 확장
        periodSeconds: 15      # 15초마다 확인
```

#### Custom Metrics (요청 수 기반)

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: main-api-hpa-custom
  namespace: default
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: main-api

  minReplicas: 2
  maxReplicas: 15

  metrics:
  - type: Pods
    pods:
      metric:
        name: http_requests_per_second
      target:
        type: AverageValue
        averageValue: "1000"  # Pod당 1000 req/s 초과 시 스케일 아웃
```

#### Prometheus 메트릭 연동

메트릭을 Prometheus에서 수집하여 HPA 결정:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: adapter-config
  namespace: kube-system
data:
  config.yaml: |
    rules:
    # HTTP 요청 수 메트릭
    - seriesQuery: 'http_requests_total{service="main-api"}'
      resources:
        overrides:
          namespace: {resource: "namespace"}
          pod: {resource: "pod"}
      name:
        matches: "^(.*)_total$"
        as: "${1}_per_second"
      metricsQuery: 'rate(<<.Series>>{<<.LabelMatchers>>}[1m])'

    # DB 쿼리 응답 시간
    - seriesQuery: 'db_query_duration_seconds'
      resources:
        overrides:
          namespace: {resource: "namespace"}
          pod: {resource: "pod"}
      name:
        as: "db_query_latency"
      metricsQuery: 'histogram_quantile(0.95, <<.Series>>)'
```

### 2. 수직 확장 (Vertical Pod Autoscaler - VPA)

#### 개념

VPA는 Pod의 리소스 요청값을 자동으로 조정하여 최적화합니다.

```
시간대별 리소스 사용 패턴:
┌─────────────────────────────────────┐
│ 피크: 오후 2-3시 (CPU 800m)          │
│ 평상: 아침 (CPU 200m)               │
│ 저사용: 야간 (CPU 100m)             │
└─────────────────────────────────────┘

VPA 최적화:
requests: 200m (평균) → 메모리 절감
limits: 800m (피크) → 성능 보장
```

#### VPA 설정

**Kubernetes 매니페스트**:

```yaml
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: summarize-ai-vpa
  namespace: default
spec:
  # 대상 Deployment
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: summarize-ai

  # 업데이트 정책
  updatePolicy:
    updateMode: "Auto"  # 자동 업데이트 (Pod 재시작 발생)
    # updateMode: "Off" 로 변경하면 권장값만 제시하고 적용 안 함

  # 리소스 제약
  resourcePolicy:
    containerPolicies:
    - containerName: summarize-ai
      # 최소/최대 범위 지정
      minAllowed:
        cpu: 500m
        memory: 512Mi
      maxAllowed:
        cpu: 4000m
        memory: 8Gi

      # 조정 대상 리소스
      controlledResources:
      - cpu
      - memory

      # 조정 제외 리소스
      controlledValues: RequestsAndLimits
```

#### VPA 권장값 확인

```bash
# VPA 권장값 조회
kubectl describe vpa summarize-ai-vpa

# 출력 예시

        Cpu:        2000m
```

### 3. Database 스케일링

**서비스에서 사용**:

```typescript
// src/services/news.service.ts
import { WriteDataSource, ReadDataSource } from '../data-source';
import { News } from '../entities/News';

class NewsService {
  // 읽기 작업: Replica 사용
  async getNews(page: number = 1, limit: number = 20) {
    const newsRepository = ReadDataSource.getRepository(News);
    return await newsRepository.find({
      skip: (page - 1) * limit,
      take: limit,
      order: { createdAt: 'DESC' },
    });
  }

  // 쓰기 작업: Master 사용
  async createNews(data: Partial<News>) {
    const newsRepository = WriteDataSource.getRepository(News);
    const news = newsRepository.create(data);
    return await newsRepository.save(news);
  }

  // 업데이트: Master 사용
  async updateNews(id: number, data: Partial<News>) {
    const newsRepository = WriteDataSource.getRepository(News);
    await newsRepository.update(id, data);
    return await newsRepository.findOneBy({ id });
  }

  // 복합 조회: Replica 사용
  async getNewsByCategory(category: string) {
    const newsRepository = ReadDataSource.getRepository(News);
    return await newsRepository.find({
      where: { category },
      order: { createdAt: 'DESC' },
    });
  }
}
```

### CloudWatch vs Prometheus 비교

#### 비용 분석

| 항목 | CloudWatch | Prometheus |

| 커스텀 메트릭 | 추가 비용 | 무료 |
| **총 비용** | **~$20/월** | **~$5/월** (저장소 제외) |

#### 선택 기준

**Prometheus 선택 이유 (FANS 프로젝트)**:
- ✅ 비용: CloudWatch 대비 75% 절감
- ✅ 유연성: 커스텀 메트릭 무제한
- ✅ 데이터 소유: AWS 외부에서 제어
- ✅ 오픈소스: 장기적 비용 절감
- ⚠️ 관리 비용: 자체 운영 필요

### 메트릭 저장소 비용 계산

```
기본 계산:
- 일 로그 생성량: 100GB (전체 서비스)
- 월 로그 생성량: 3,000GB (3TB)
- 보관 기간: 30일

Prometheus (TSDB):
  메트릭 저장 공간: 50GB (설정)
  비용: 저장소만 계산 ($0.023/GB) = $1.15/월

Loki (S3 기반):
  S3 저장 비용: 3,000GB × $0.023 = $69/월
  Loki 수집 비용: 무료
  총 비용: $69/월

CloudWatch 대비:
  CloudWatch 로그: $5 (10GB) × 30 = $150/월
  절감액: $150 - $69 = $81/월 (46% 절감)
```
