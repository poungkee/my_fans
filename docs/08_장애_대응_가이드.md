## 장애 시나리오

### 1. Database 장애

#### 증상
- API 응답 타임아웃 (>30초)
- 500 Internal Server Error 증가
- Prometheus Alert: `PostgreSQL Down`
- 데이터베이스 연결 풀 고갈

#### 원인 파악

**1단계: DB 연결 상태 확인**

```bash
# 로컬 환경
psql -h localhost -p 5432 -U postgres -d fans -c "SELECT 1"

# 도커 환경
docker exec fans_postgres pg_isready -h localhost -p 5432 -U postgres

# Kubernetes 환경
kubectl exec -it deployment/main-api -- \
  pg_isready -h postgres -p 5432 -U postgres
```

**2단계: 데이터베이스 로그 확인**

```bash
# 도커 로그
docker logs fans_postgres --tail=100

# Kubernetes 로그
kubectl logs deployment/postgres -n database --tail=100
```

**3단계: 연결 수 및 리소스 확인**

```bash
# 현재 활성 연결 수
psql -c "SELECT count(*) FROM pg_stat_activity;"

# 연결 상세 정보
psql -c "SELECT usename, client_addr, state FROM pg_stat_activity;"

# 메모리 사용량 (Docker)
docker stats fans_postgres

# Pod 리소스 사용량 (Kubernetes)
kubectl top pod -n database
```

**4단계: Disk 공간 확인**

```bash
# 데이터베이스 크기
psql -c "\l+"

# 테이블 크기
psql -c "\dt+ public.*"

# Disk 여유 공간 (Docker)
docker exec fans_postgres df -h /var/lib/postgresql/data
```

#### 복구 절차

**옵션 1: Pod/컨테이너 재시작 (경미한 장애)**

```bash
# 도커 환경
docker restart fans_postgres
docker restart fans_main_api

# Kubernetes 환경
kubectl rollout restart deployment/main-api
kubectl rollout restart statefulset/postgres -n database

# 상태 확인
kubectl rollout status deployment/main-api
```

**옵션 2: 데이터베이스 재시작 (연결 풀 고갈)**

```bash
# PostgreSQL 재시작
docker restart fans_postgres

# 또는 강제 재시작
docker kill fans_postgres && docker start fans_postgres

# 연결 확인
psql -c "SELECT count(*) FROM pg_stat_activity;"
```

**옵션 3: 컨트롤러 재설정 (심각한 장애)**

```bash
# 데이터베이스 상태 확인
pg_controldata /var/lib/postgresql/data

# 데이터베이스 초기화 (데이터 손실 주의!)
sudo -u postgres pg_resetwal /var/lib/postgresql/data

# 서비스 재시작
docker restart fans_postgres
```

**옵션 4: RDS 페일오버 (프로덕션 환경)**

```bash
# AWS RDS 페일오버
aws rds reboot-db-instance \
  --db-instance-identifier fans-postgres \
  --force-failover

# 상태 모니터링
aws rds describe-db-instances \
  --db-instance-identifier fans-postgres \
  --query 'DBInstances[0].DBInstanceStatus'
```

**옵션 4: 모델 최적화 (OOM 해결)**

```python
# PyTorch 모델 최적화 코드 예제
# backend/ai-worker/summarize/optimize.py

import torch
from transformers import AutoModelForSeq2SeqLM

def optimize_model(model_path):
    """
    모델 양자화 및 최적화
    """
    model = AutoModelForSeq2SeqLM.from_pretrained(model_path)

    # 모델 양자화 (Int8)
    model = torch.quantization.quantize_dynamic(
        model,
        {torch.nn.Linear},
        dtype=torch.qint8
    )

    model.save_pretrained('./quantized_model')
    return model

# 배치 크기 감소 및 메모리 최적화
# config.yml
inference:
  batch_size: 4  # 16에서 4로 감소
  max_length: 256
  num_beams: 2  # 4에서 2로 감소
  use_cache: false  # KV cache 비활성화
```

## Rollback 절차

### 자동 Rollback (Kubernetes)

#### 배포 이력 확인

```bash
# 배포 이력 확인
kubectl rollout history deployment/main-api

# 특정 버전의 상세 정보 확인
kubectl rollout history deployment/main-api --revision=5

# 배포 이력 다세부 정보
kubectl rollout history deployment/main-api -o yaml
```

#### 이전 버전으로 Rollback

```bash
# 가장 최근 이전 버전으로 롤백
kubectl rollout undo deployment/main-api

# 특정 버전으로 롤백
kubectl rollout undo deployment/main-api --to-revision=3

# 롤백 진행 상황 모니터링
kubectl rollout status deployment/main-api --watch

# 롤백 완료 확인
kubectl get deployment main-api -o wide
```

#### Rollback 완료 확인

```bash
# 배포된 이미지 버전 확인
kubectl get deployment main-api -o jsonpath='{.spec.template.spec.containers[0].image}'

# Pod 상태 확인
kubectl get pods -l app=main-api

# 서비스 정상 동작 확인
curl -H "Authorization: Bearer $TOKEN" http://api.fans.ai.kr/api/health
```

### 수동 Rollback (직접 이미지 변경)

#### 현재 배포 정보 확인

```bash
# 현재 이미지 확인
kubectl get deployment main-api -o yaml | grep image:

# 최근 배포 이미지 확인
kubectl describe deployment main-api | grep Image:
```

#### 안정 버전으로 직접 변경

```bash
# 안정 버전의 이미지 태그 설정
kubectl set image deployment/main-api \
  main-api=123456789.dkr.ecr.ap-northeast-2.amazonaws.com/fans/main-api:v1.2.0 \
  --record

# 또는 여러 컨테이너가 있는 경우
kubectl set image deployment/main-api \
  main-api=<image1:tag1> \
  worker=<image2:tag2> \
  --record

# 배포 상태 모니터링
kubectl rollout status deployment/main-api --watch
```

#### ConfigMap/Secret 복원

```bash
# 이전 버전의 ConfigMap 복원
kubectl apply -f environments/eks/manifests/03-configmap.yaml

# 이전 버전의 Secret 복원
```

### Rollback 코드 예제

#### Node.js API 에러 처리 및 Graceful Rollback

```javascript
// backend/api/src/middleware/errorHandler.ts
import express from 'express';
import { logger } from '../utils/logger';

export const errorHandler = (
  err: Error,
  req: express.Request,
  res: express.Response,
  next: express.NextFunction
) => {
  logger.error('Request Error', {
    path: req.path,
    method: req.method,
    error: err.message,
    stack: err.stack,
    timestamp: new Date().toISOString(),
  });

  // 순환 참조 방지를 위해 순환 에러는 특별 처리
  if (err.message.includes('CIRCULAR')) {
    logger.warn('Circular reference detected - initiating rollback');
    return res.status(500).json({
      error: 'Internal Server Error',
      message: 'Critical error detected - triggering rollback',
      requestId: req.id,
    });
  }

  // 치명적 에러 - rollback 트리거
  if (err.message.includes('FATAL') || err.name === 'FatalError') {
    logger.critical('Fatal error detected', { error: err });

    // Rollback 신호 전송 (외부 모니터링 시스템으로)
    triggerRollback();

    return res.status(503).json({
      error: 'Service Unavailable',
      message: 'Critical system error - rollback in progress',
    });
  }

  const status = err.statusCode || 500;
  res.status(status).json({
    error: err.name,
    message: err.message,
    requestId: req.id,
  });
};

function triggerRollback() {
  // 외부 모니터링/Kubernetes API 호출
  fetch('http://localhost:8000/api/rollback', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({
      deployment: 'main-api',
      reason: 'FATAL_ERROR',
      timestamp: new Date().toISOString(),
    }),
  }).catch(err => logger.error('Rollback trigger failed', err));
}
```

#### Kubernetes Rollback 자동화 스크립트

```bash
#!/bin/bash
# environments/eks/scripts/auto-rollback.sh

set -e

DEPLOYMENT=$1
NAMESPACE=${2:-default}
REVISION=${3:-0}  # 0이면 이전 버전으로

log() {
  echo "[$(date +'%Y-%m-%d %H:%M:%S')] $1"
}

# 현재 배포 상태 확인
log "Checking deployment status..."
STATUS=$(kubectl get deployment $DEPLOYMENT -n $NAMESPACE -o jsonpath='{.status.conditions[?(@.type=="Progressing")].status}')

if [ "$STATUS" != "True" ]; then
  log "Deployment failed or stuck. Initiating rollback..."

  # 이전 버전 확인
  if [ "$REVISION" == "0" ]; then
    REVISION=$(kubectl rollout history deployment/$DEPLOYMENT -n $NAMESPACE | tail -2 | head -1 | awk '{print $1}')
  fi

  # Rollback 실행
  log "Rolling back to revision $REVISION..."
  kubectl rollout undo deployment/$DEPLOYMENT --to-revision=$REVISION -n $NAMESPACE

  # 롤백 대기
  log "Waiting for rollback to complete..."
  kubectl rollout status deployment/$DEPLOYMENT -n $NAMESPACE --timeout=5m

  log "Rollback completed successfully!"
  exit 0
else
  log "Deployment is healthy. No rollback needed."
  exit 0
fi
```

```bash
#!/bin/bash
# environments/eks/scripts/dr-test.sh

set -e

log() {
  echo "[DR Test] $(date +'%Y-%m-%d %H:%M:%S') - $1"
}

log "Starting DR recovery test..."

# 1. 백업 확인
log "Verifying backup availability..."
BACKUP_COUNT=$(aws s3 ls s3://fans-backups/db/ | wc -l)
if [ $BACKUP_COUNT -eq 0 ]; then
  log "ERROR: No backups found!"
  exit 1
fi

# 2. 테스트 DB 생성
log "Creating test database..."
psql -c "DROP DATABASE IF EXISTS fans_dr_test;"
psql -c "CREATE DATABASE fans_dr_test OWNER postgres;"

# 3. 최근 백업 다운로드
log "Downloading latest backup..."
LATEST_BACKUP=$(aws s3 ls s3://fans-backups/db/ | sort | tail -1 | awk '{print $NF}')
aws s3 cp "s3://fans-backups/db/$LATEST_BACKUP" ./

# 4. 테스트 DB에 복원
log "Restoring backup to test database..."
pg_restore -h localhost -U postgres \
  -d fans_dr_test \
  -c -v "$LATEST_BACKUP" || {
  log "ERROR: Restore failed!"
  psql -c "DROP DATABASE fans_dr_test;"
  exit 1
}

# 5. 데이터 검증
log "Validating restored data..."
RESTORED_COUNT=$(psql -U postgres -d fans_dr_test -c "SELECT COUNT(*) FROM news_articles;" | grep -oP '\d+' | head -1)
ORIGINAL_COUNT=$(psql -U postgres -d fans -c "SELECT COUNT(*) FROM news_articles;" | grep -oP '\d+' | head -1)

if [ "$RESTORED_COUNT" -eq "$ORIGINAL_COUNT" ]; then
  log "SUCCESS: Data validation passed!"
  log "Original count: $ORIGINAL_COUNT, Restored count: $RESTORED_COUNT"
else
  log "WARNING: Data count mismatch!"
  log "Original count: $ORIGINAL_COUNT, Restored count: $RESTORED_COUNT"
fi

# 6. 테스트 DB 정리
log "Cleaning up test database..."
psql -c "DROP DATABASE fans_dr_test;"
rm -f "$LATEST_BACKUP"

log "DR recovery test completed!"
```

### 자주 발생하는 문제

| 증상 | 원인 | 해결 방법 |
|------|------|---------|
| API 타임아웃 | DB 연결 풀 고갈 | Pod 재시작, 연결 풀 설정 조정 |
| OOM 에러 | AI 모델 메모리 부족 | Pod 메모리 증가, 배치 크기 감소 |
| DNS 오류 | CoreDNS 서비스 다운 | CoreDNS 재시작, DNS 캐시 플러시 |
| 404 Not Found | Ingress 설정 오류 | Ingress Controller 재시작, 경로 확인 |
| 503 Service Unavailable | 백엔드 서비스 다운 | 해당 서비스 Pod 재시작 |
