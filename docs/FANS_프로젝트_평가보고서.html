Executive Summary

FANS(Filtering & Analysis News System)는 뉴스 데이터를 자동으로 수집하고, AI가 이를 요약하고 편향성을 분석해 사용자가 신뢰성 있는 뉴스를 빠르게 파악할 수 있도록 돕는 AI 뉴스 큐레이션 플랫폼입니다.

플랫폼은 AWS EKS를 중심으로 운영되며, KEDA + HPA + Karpenter로 구성된 3단계 오토스케일링 시스템을 통해 트래픽 증가나 대기 작업이 발생하더라도 즉시 리소스를 확장할 수 있습니다. EKS 클러스터는 Multi-AZ 환경에서 운영되어 고가용성을 확보하고 있으며, PostgreSQL RDS, ElastiCache Redis, CloudFront, Route 53 등 AWS 주요 서비스와 통합되어 안정성과 확장성을 모두 달성했습니다.

  • ✅ 완전 자동화: 크롤링 → AI 처리 → 저장까지 사람 개입 0%
  • ✅ 비용 효율성: v1.0 대비 75% 메모리 절감, KEDA로 79% Pod 비용 절감
  • ✅ 고가용성: Multi-AZ 배포로 99.9% 가동률 보장

최종 의사결정 근거

핵심 결정 요인:

  1. 큐 기반 오토스케일링 필수성:
    • AI 처리 작업은 BullMQ 큐에 저장되며, 큐 길이에 따라 Worker 수를 동적으로 조정해야 함
    • ECS의 CloudWatch Alarm 기반 스케일링은 반응 속도가 느림 (1~2분 지연)
    • KEDA는 큐 길이를 실시간으로 모니터링하여 15초 내 스케일링 가능
  2. 비용 효율성 (장기적 관점):
    • 초기 Control Plane 비용 $73/월이 추가되지만
    • KEDA로 AI Worker Pod 비용 79% 절감 → 월 $150 절감
    • Karpenter Spot 인스턴스로 EC2 비용 70% 절감
    • 순 절감액: 월 $77+ (초기 비용 상쇄)
  3. 미래 확장성:
    • Kubernetes는 온프레미스, 다른 클라우드로 이식 가능
    • Multi-Region 배포 시 동일한 manifest 재사용 가능
    • 오픈소스 생태계 활용 (Prometheus, Grafana, ArgoCD 등)
  4. 팀 역량 강화:
    • Kubernetes는 업계 표준 기술로 학습 가치가 높음
    • 초기 러닝 커브는 높지만 장기적으로 팀 경쟁력 향상

ECS 구현 경험 활용

ECS 환경에서 얻은 인사이트가 EKS 설계에 반영되었습니다:

  • Task Definition 경험 → Kubernetes Deployment YAML 설계
  • Service Discovery 이해 → Kubernetes Service 및 Ingress 설정
  • CloudWatch Logs 통합 경험 → EKS Logging 구성
  • Fargate 제한사항 파악 → EC2 노드 그룹 전략 수립

결론

초기 비용과 복잡성에도 불구하고, 큐 기반 동적 스케일링, 장기 비용 절감, 미래 확장성을 고려하여 Amazon EKS를 최종 선택했습니다. 실제 운영 결과, KEDA + Karpenter 조합으로 예상보다 높은 비용 효율성을 달성했습니다.

5. 3단계 오토스케일링

5.1 1단계: HPA (Horizontal Pod Autoscaler)

대상: Main API
메트릭: CPU 50%, Memory 70%
범위: 2~10 Pod

  • CPU 50% 초과 → Pod 추가 (최대 100% 증가, 15초마다)
  • 메모리 70% 초과 → Pod 추가
  • 부하 감소 → 60초 대기 후 50%씩 축소 (30초마다)

효과: 트래픽 증가 시 API 서버 자동 확장

5.2 2단계: KEDA (Kubernetes Event Driven Autoscaler)

대상: AI Worker
트리거: Redis 큐 길이
범위: 1~20 Pod

  • 큐 길이 0~4: 1개 Pod (최소)
  • 큐 길이 5~9: 2개 Pod (5개당 1개 규칙)
  • 큐 길이 10~14: 3개 Pod
  • 큐 길이 100+: 20개 Pod (최대)

스케일링 시나리오

08:00 - 큐: 0개, Pod: 1개 (대기)
10:30 - 크롤러 실행, 큐: 240개 추가
10:31 - KEDA 감지, Pod: 20개로 스케일 업 (최대)
10:35 - 병렬 처리 중, 큐: 180개
10:45 - 큐: 60개, Pod: 12개로 축소
10:55 - 큐: 0개
11:00 - 5분 대기 후 Pod: 1개로 축소

비용 절감 효과

  • 기존 (20개 상시): 14,400 Pod-시간/월
  • KEDA (동적): 3,000 Pod-시간/월
  • 절감률: 79%

5.3 3단계: Karpenter (노드 레벨 스케일링)

역할: EC2 인스턴스 자동 생성/삭제
트리거: Pod Pending (노드 부족)
인스턴스: Spot 우선 (70% 절감)

동작 흐름

NodePool 구성

  • General NodePool: On-Demand (안정성 중요, t3.medium~large)
  • AI Worker NodePool: Spot (비용 절감, c5/c6i.xlarge)

on:
  push:
    branches: [main]
    paths:
      - 'backend/api/**'

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v3

      - name: Setup Node.js 20
        uses: actions/setup-node@v3
        with:
          node-version: '20'

      - name: Run Tests
        run: |
          cd backend/api
          npm install
          npm test

      - name: Configure AWS Credentials
        uses: aws-actions/configure-aws-credentials@v2
        with:
          aws-region: ap-northeast-2

      - name: Login to ECR
        run: |
          aws ecr get-login-password --region ap-northeast-2 | \
          docker login --username AWS --password-stdin ECR_URL

      - name: Build & Push Docker Image
        run: |
          cd backend/api
          docker build -t main-api:${{ github.sha }} .
          docker tag main-api:${{ github.sha }} ECR_URL/main-api:latest
          docker push ECR_URL/main-api:latest

      - name: Deploy to EKS
        run: |
          aws eks update-kubeconfig --name fans-cluster --region ap-northeast-2
          kubectl set image deployment/main-api \
            main-api=ECR_URL/main-api:latest
          kubectl rollout status deployment/main-api --timeout=5m

      - name: Notify Slack (Success)
        if: success()
        run: |
          curl -X POST ${{ secrets.SLACK_WEBHOOK }} \
          -d '{"text":"✅ Main API 배포 완료: ${{ github.sha }}"}'

      - name: Rollback & Notify (Failure)
        if: failure()
        run: |
          kubectl rollout undo deployment/main-api
          curl -X POST ${{ secrets.SLACK_WEBHOOK }} \
          -d '{"text":"❌ Main API 배포 실패. 자동 롤백 완료"}'

1단계: Grafana 대시보드 확인

  • Worker Node의 여유 리소스 부족 (총 4GB 중 3.5GB 사용 중)

5.3.4 근본 원인 해결 (30분)

중기 조치: Worker Node 리소스 스케일링

문제: Worker Node의 총 리소스가 부족해 Pod가 리소스를 충분히 할당받지 못함

해결:

  1. Karpenter NodePool 수정 (즉시 반영) 
    # NodePool에 더 큰 인스턴스 타입 추가
instanceTypes:
  - t3.medium
  - t3.large    # 기존
  - t3.xlarge   # 추가 (CPU 4코어, 메모리 16GB)

    $ kubectl drain ip-10-0-1-45 --ignore-daemonsets

# Karpenter가 자동으로 t3.xlarge 노드 생성 (1~2분)
$ kubectl get nodes

ip-10-0-1-120.ap-northeast-2.compute.internal   Ready    <none>   3m   # t3.xlarge
  3. Pod 자동 재배치 
    # Kubernetes가 자동으로 새 노드에 Pod 배치
$ kubectl get pods -o wide | grep unified-crawler
unified-crawler-7b8f9d5c-xyz   1/1   Running   0   ip-10-0-1-120

결과:

  • Worker Node CPU: 4코어 (여유 50%)
  • Worker Node 메모리: 16GB (여유 60%)
  • Pod 안정성 확보 (메모리 2GB limits, 실제 사용 900MB)

5.3.5 재발 방지 조치

장기 조치

  1. 리소스 Requests/Limits 재검토
    • 모든 서비스의 실제 사용량 측정 (7일 평균)
    • Requests: 평균 사용량 × 1.2
    • Limits: 피크 사용량 × 1.5
  2. Vertical Pod Autoscaler (VPA) 검토
    • Pod의 리소스를 자동으로 조정
    • 메모리 부족 시 자동으로 limits 증가
  3. 알림 임계값 조정
    • 메모리 사용률 > 70% → Warning 알림 추가
    • 메모리 사용률 > 85% → Critical 알림 (기존 80%에서 조정)
  4. Karpenter 설정 최적화
    • NodePool에 다양한 인스턴스 타입 추가 (t3.medium ~ c5.2xlarge)
    • 리소스 부족 시 자동으로 더 큰 노드 생성

교훈

  • ✅ 모니터링의 중요성: Prometheus/Grafana 덕분에 5분 내 원인 파악
  • ✅ 자동화된 알림: Slack 알림으로 장애를 즉시 인지
  • ✅ 빠른 대응: kubectl 명령으로 5분 내 즉각 복구
  • ✅ 근본 해결: 단순 재시작이 아닌 노드 리소스 확장으로 재발 방지
