## 문제 상황

### 현재 문제점
- **요약 백로그**: 6,489개 과거 기사가 요약 대기 중
- **실시간 유입**: 하루 평균 3,187개 신규 기사 수집
- **처리 병목**: Scheduler가 과거 + 실시간 기사를 모두 큐에 추가하여 처리 지연 발생
- **리소스 부족**: summarize-ai Pod 2개가 Pending 상태 (노드 리소스 부족)

### 데이터 분석 (2025-11-04 기준)
```
전체 기사: 15,935개
요약 완료: 9,446개 (59.3%)
요약 대기: 6,489개 (40.7%)

일일 수집량:
- 평균: 3,187개/일 (133개/시간)
- 최대: 5,115개/일 (213개/시간)
```

## 고려한 솔루션

### 방안 1: Karpenter를 통한 자동 확장
**개념**:
- Kubernetes 노드 자동 확장 솔루션
- Pod 리소스 부족 시 자동으로 EC2 인스턴스 추가
- Spot 인스턴스 활용으로 비용 절감

**장점**:
- 완전 자동 확장 (무한한 처리 능력)
- Spot 인스턴스로 70% 비용 절감
- 트래픽 급증 시 자동 대응

**단점**:
- **VPC Endpoint 구성 필수** (NAT Gateway 없이 Private Subnet 운영)
  - com.amazonaws.ap-northeast-2.eks
  - com.amazonaws.ap-northeast-2.sts
  - com.amazonaws.ap-northeast-2.ec2
  - com.amazonaws.ap-northeast-2.ecr.api
  - com.amazonaws.ap-northeast-2.ecr.dkr
  - com.amazonaws.ap-northeast-2.s3 (Gateway)
- **EKS 1.31과 Karpenter v0.36 버전 호환 문제**
- **v1.0.6 이상으로 업그레이드 필요**
- **복잡한 네트워크 설정** (PrivateLink, Security Group, Endpoint Policy)

---

### 방안 2: BullMQ + 배치 스케줄 분리 (최종 선택)
**개념**:
- 실시간 처리: 오늘 기사만 즉시 큐 추가
- 배치 처리: 과거 기사는 야간 CronJob으로 분리 처리

**장점**:
- **간단한 구현** (쿼리 수정 + CronJob 추가)
- **추가 비용 없음** (기존 인프라 활용)
- **빠른 배포** (3-5시간)
- **안정적 운영** (검증된 BullMQ + Kubernetes CronJob)

**단점**:
- 백로그 처리 기간 (약 7일 소요)
- 수동 확장 필요 (트래픽 10배 증가 시)

## 최종 선택: BullMQ + 배치 스케줄

### 선택 이유

#### 1. 처리 능력 충분
```
Worker 처리 능력:
- ai-worker Pod 2개
- 각 Worker: 900개/시간 (concurrency=1, 평균 4초/기사)
- 총 처리 능력: 1,800개/시간 = 43,200개/일

실제 수요:
- 평균: 133개/시간 (3,187개/일)
- 피크: 213개/시간 (5,115개/일)

여유율:
- 평균: 13.5배
- 피크: 8.4배
```

**→ 현재 리소스로 충분히 처리 가능!**

#### 2. 비용 효율성
Karpenter를 도입하지 않아도 되는 이유:
- 현재 처리 능력이 수요의 **8배 이상**
- 백로그는 일회성 문제 (과거 데이터)
- 실시간 유입은 기존 인프라로 처리 가능

#### 3. 구현 단순성
- Scheduler 쿼리 1줄 수정
- 배치 스크립트 1개 추가
- CronJob YAML 1개 추가

#### 4. 안정성
- BullMQ: 검증된 큐 시스템
- Kubernetes CronJob: 검증된 스케줄링
- 기존 인프라 활용으로 안정성 확보

## 구현 내역

### 1. Scheduler 수정
**파일**: `backend/scheduler/src/jobs/generateSummaries.ts`

**변경 내용**:
```typescript
// 변경 전
WHERE ai_summary IS NULL
  AND content IS NOT NULL
  AND LENGTH(content) >= 100

// 변경 후
WHERE ai_summary IS NULL
  AND content IS NOT NULL
  AND LENGTH(content) >= 100
  AND created_at >= CURRENT_DATE  -- 오늘 기사만!
```

**효과**: 과거 기사와 실시간 기사 분리

---

### 2. 배치 백로그 처리 스크립트
**파일**: `backend/scheduler/src/batch-backlog.ts`

**주요 기능**:
- 과거 기사(created_at < CURRENT_DATE) 1,000개 조회
- BullMQ 큐에 배치 추가
- 전체 백로그 진행률 표시
- 예상 완료 일수 계산

**실행 환경**: Kubernetes CronJob

---

### 3. Kubernetes CronJob
**파일**: `environments/eks/manifests/13-batch-summary-backlog.yaml`

**설정**:
```yaml
schedule: "0 2 * * *"  # 매일 새벽 2시
concurrencyPolicy: Forbid  # 동시 실행 방지
activeDeadlineSeconds: 21600  # 6시간 타임아웃
backoffLimit: 3  # 3번 재시도
```

**리소스**:
```yaml
requests:
  memory: 256Mi
  cpu: 250m
limits:
  memory: 512Mi
  cpu: 500m
```

## 예상 효과

### 1. 실시간 처리 개선
```
현재: 과거 + 실시간 혼재 → 처리 지연
개선: 실시간만 처리 → 1-5분 내 요약 완료
```

### 2. 백로그 처리
```
Day 1: 1,000개 처리 (남은 백로그: 5,489개)
Day 2: 1,000개 처리 (남은 백로그: 4,489개)
Day 3: 1,000개 처리 (남은 백로그: 3,489개)
Day 4: 1,000개 처리 (남은 백로그: 2,489개)
Day 5: 1,000개 처리 (남은 백로그: 1,489개)
Day 6: 1,000개 처리 (남은 백로그: 489개)
Day 7: 489개 처리 (백로그 완료! ✅)
```

### 3. 사용자 경험
```
실시간 기사:
- 기존: 수 시간 ~ 며칠 지연
- 개선: 1-5분 내 요약 제공

과거 기사:
- 기존: 요약 없음 (fallback 요약만)
- 개선: 7일 내 AI 요약 제공
```

### 4. 리소스 효율
```
기존:
- summarize-ai Pod: Pending (리소스 부족)
- Worker: 과부하 상태

개선:
- summarize-ai Pod: Running (기존 노드 활용)
- Worker: 여유율 13.5배 (안정적)
```
