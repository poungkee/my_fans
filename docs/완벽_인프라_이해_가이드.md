## 1. AWS 인프라 구조

### 1.1 VPC (Virtual Private Cloud)

#### 왜 필요한가?
- VPC는 AWS에서 나만의 "가상 데이터 센터"를 만드는 것입니다
- 비유: 아파트 단지를 생각하면 됩니다. 외부와 격리된 안전한 공간이죠

#### 어떻게 작동하는가?
```
VPC (10.0.0.0/16)
│
├── Public Subnet (인터넷 연결 가능)
│   ├── 10.0.101.0/24 (ap-northeast-2a)
│   └── 10.0.102.0/24 (ap-northeast-2b)
│
├── Private Subnet (인터넷 차단, 내부만)
│   ├── 10.0.1.0/24 (ap-northeast-2a)
│   └── 10.0.2.0/24 (ap-northeast-2b)
│
├── Database Subnet (RDS 전용)
│   ├── 10.0.201.0/24 (ap-northeast-2a)
│   └── 10.0.202.0/24 (ap-northeast-2b)
│
└── ElastiCache Subnet (Redis 전용)
    ├── 10.0.211.0/24 (ap-northeast-2a)
    └── 10.0.212.0/24 (ap-northeast-2b)
```

#### 어떤 파일에 설정되어 있는가?
- **파일**: `D:\dev1\environments\eks\terraform\vpc.tf`
- **핵심 코드**:
```hcl
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"

  cidr = "10.0.0.0/16"  # 전체 VPC IP 범위

  # 2개의 가용 영역 사용 (서울: 2a, 2b)
  azs = ["ap-northeast-2a", "ap-northeast-2b"]

  # Private Subnets: Worker 노드가 여기 배치됨
  private_subnets = ["10.0.1.0/24", "10.0.2.0/24"]

  # Public Subnets: ALB가 여기 배치됨
  public_subnets = ["10.0.101.0/24", "10.0.102.0/24"]

  # Database Subnets: RDS가 여기 배치됨
  database_subnets = ["10.0.201.0/24", "10.0.202.0/24"]

  # ElastiCache Subnets: Redis가 여기 배치됨
  elasticache_subnets = ["10.0.211.0/24", "10.0.212.0/24"]
}
```

#### 실제 예시
- Public Subnet: ALB가 인터넷에서 요청 받음
- Private Subnet: EKS Worker 노드가 안전하게 작동
- Database Subnet: RDS PostgreSQL이 외부 접근 차단
- ElastiCache Subnet: Redis가 내부 통신만 가능

### 1.2 서브넷 (Subnet)

#### 왜 필요한가?
- VPC를 여러 구역으로 나누어 보안과 가용성 확보
- 비유: 아파트 단지를 "주거동", "상가동", "관리동"으로 나누는 것

#### Public vs Private Subnet 차이

| 구분 | Public Subnet | Private Subnet |
|------|---------------|----------------|
| 인터넷 접근 | 가능 (IGW 연결) | 불가능 (NAT로만 외부 연결) |
| 배치 대상 | ALB, NAT Gateway | EKS Worker, RDS, Redis |
| IP 범위 | 10.0.101.0/24, 10.0.102.0/24 | 10.0.1.0/24, 10.0.2.0/24 |
| 용도 | 외부 트래픽 수신 | 내부 서비스 실행 |

#### 실제 예시
```
사용자 요청 흐름:
1. 사용자 → Public Subnet (ALB)
2. ALB → Private Subnet (EKS Pod)
3. EKS Pod → Database Subnet (RDS)
```

### 1.3 인터넷 게이트웨이 (IGW)

#### 왜 필요한가?
- VPC와 인터넷을 연결하는 "정문"
- 비유: 아파트 단지의 정문 게이트

#### 어떻게 작동하는가?
```
인터넷
  ↓
Internet Gateway (IGW)
  ↓
Public Subnet (ALB)
  ↓
Private Subnet (EKS)
```

#### 어떤 파일에 설정되어 있는가?
- **파일**: `D:\dev1\environments\eks\terraform\vpc.tf`
- **자동 생성**: VPC 모듈이 자동으로 IGW 생성
- **라우팅**: Public Subnet의 라우팅 테이블에 `0.0.0.0/0 → IGW` 규칙 추가

---

### 1.4 NAT 게이트웨이 (NAT Gateway)

#### 왜 필요한가?
- Private Subnet의 리소스가 인터넷에 접근할 수 있게 함 (단방향)
- 비유: 아파트 거주자는 밖에 나갈 수 있지만, 외부인은 못 들어옴

#### 어떻게 작동하는가?
```
Private Subnet (EKS Pod)
  ↓ (외부 API 호출, npm install 등)
NAT Gateway (Public Subnet에 위치)
  ↓
Internet Gateway
  ↓
인터넷
```

#### Multi-AZ NAT Gateway 설정
```hcl
# 각 AZ마다 NAT Gateway 1개씩 (총 2개)
enable_nat_gateway = true
single_nat_gateway = false  # false = 2개
one_nat_gateway_per_az = true
```

#### 실제 예시
- EKS Pod가 `npm install` 실행 → NAT Gateway → 인터넷 → npm 레지스트리
- AI 서비스가 Hugging Face API 호출 → NAT Gateway → 인터넷

#### 비용
- NAT Gateway: $32/월 (1개당)
- Multi-AZ (2개): $64/월
- 고가용성을 위해 필수!

---

### 1.5 라우팅 테이블 (Route Table)

#### 왜 필요한가?
- 네트워크 트래픽의 "도로 지도"
- 어떤 IP로 가려면 어디로 가야 하는지 알려줌

#### Public Subnet 라우팅 테이블
```
목적지           다음 홉
10.0.0.0/16  →  local      (VPC 내부)
0.0.0.0/0    →  igw-xxx    (인터넷)
```

#### Private Subnet 라우팅 테이블
```
목적지           다음 홉
10.0.0.0/16  →  local      (VPC 내부)
0.0.0.0/0    →  nat-xxx    (NAT Gateway)
```

#### 실제 예시
- EKS Pod (10.0.1.50) → RDS (10.0.201.10): VPC 내부 통신 (local)
- EKS Pod → www.google.com: NAT Gateway → Internet

### 1.6 보안 그룹 (Security Group)

#### 왜 필요한가?
- 리소스별 "방화벽" 역할
- 비유: 각 건물마다 다른 출입 카드 규칙

#### FANS 프로젝트의 보안 그룹

| 보안 그룹 | 용도 | 인바운드 규칙 | 파일 |
|-----------|------|--------------|------|
| ALB SG | Load Balancer | HTTP(80), HTTPS(443) from 0.0.0.0/0 | alb.tf |
| EKS Node SG | Worker 노드 | All from ALB SG, All from self | eks.tf |
| RDS SG | PostgreSQL | 5432 from EKS Node SG | rds.tf |
| ElastiCache SG | Redis | 6379 from EKS Node SG | elasticache.tf |

#### 실제 보안 그룹 코드
```hcl
# RDS 보안 그룹
resource "aws_security_group" "rds" {
  name_prefix = "fans-cluster-rds-sg"
  vpc_id      = module.vpc.vpc_id

  # PostgreSQL 포트만 EKS 노드에서 접근 허용
  ingress {
    description     = "PostgreSQL from EKS nodes"
    from_port       = 5432
    to_port         = 5432
    protocol        = "tcp"
    security_groups = [module.eks.node_security_group_id]
  }
}
```

#### 실제 예시
- 사용자가 직접 RDS 접근 시도 → 차단 (EKS 노드만 허용)
- EKS Pod → RDS 접근 → 허용 (같은 보안 그룹)

---

### 1.7 NACL (Network ACL)

#### 왜 필요한가?
- 서브넷 단위 방화벽 (보안 그룹보다 상위)
- 비유: 보안 그룹 = 건물 보안, NACL = 단지 보안

#### FANS 프로젝트에서는?
- **현재 사용 안 함** (기본 NACL 사용)
- 보안 그룹만으로 충분히 보안 확보
- 필요 시 추가 가능

## 2. EKS 클러스터 구조

### 2.1 Control Plane (관리자)

#### 왜 필요한가?
- Kubernetes의 "두뇌" 역할
- 모든 노드를 관리하고 명령을 내림

#### 어떻게 작동하는가?
```
Control Plane (AWS가 관리)
├── API Server (kubectl 요청 처리)
├── Scheduler (Pod를 어느 노드에 배치할지 결정)
├── Controller Manager (Deployment, Service 관리)
└── etcd (모든 상태 저장)
```

#### 어떤 파일에 설정되어 있는가?
- **파일**: `D:\dev1\environments\eks\terraform\eks.tf`
- **핵심 코드**:
```hcl
module "eks" {
  cluster_name    = "fans-cluster"
  cluster_version = "1.31"

  # Control Plane이 배치될 서브넷
  control_plane_subnet_ids = module.vpc.private_subnets

  # 로깅 활성화
  cluster_enabled_log_types = ["api", "audit", "authenticator"]
}
```

#### 실제 예시
- `kubectl apply -f deployment.yaml` → API Server → Scheduler → 노드 선택
- Pod가 죽음 → Controller Manager → 새 Pod 생성

#### 비용
- EKS Control Plane: $73/월 (고정 비용)

---

### 2.2 Worker Nodes (일꾼)

#### 왜 필요한가?
- 실제 애플리케이션(Pod)이 실행되는 "컴퓨터"
- 비유: 사무실의 직원 컴퓨터

#### FANS 프로젝트의 노드 구성

| 노드 그룹 | 인스턴스 타입 | 개수 | 용도 | AZ 분산 |
|-----------|--------------|------|------|---------|
| General Workers | t3.large | 2개 고정 | main-api, scheduler, crawler | 2a(1), 2b(1) |
| AI Workers | t3a.xlarge | 2개 고정 | summarize-ai, bias-ai | 2a(1), 2b(1) |

#### 어떤 파일에 설정되어 있는가?
- **파일**: `D:\dev1\environments\eks\terraform\eks.tf`
- **핵심 코드**:
```hcl
eks_managed_node_groups = {
  # General Workers: 일반 서비스
  general_workers = {
    instance_types = ["t3.large"]
    min_size     = 2
    max_size     = 2
    desired_size = 2

    labels = {
      role     = "general-worker"
      workload = "general"
    }
  }

  # AI Workers: AI 서비스
  ai_workers = {
    instance_types = ["t3a.xlarge"]
    min_size     = 2
    max_size     = 2
    desired_size = 2

    labels = {
      role     = "ai-worker"
      workload = "ai"
    }
  }
}
```

#### 노드 스펙 비교

| 인스턴스 | vCPU | RAM | 디스크 | 용도 | 비용 |
|----------|------|-----|--------|------|------|
| t3.large | 2 | 8GB | 50GB | 일반 서비스 | $60/월 |
| t3a.xlarge | 4 | 16GB | 50GB | AI 서비스 | $120/월 |

#### 실제 예시
- main-api Pod → General Worker 노드에 배치
- summarize-ai Pod → AI Worker 노드에 배치 (메모리 많이 필요)

### 2.3 노드 그룹 종류 및 역할

#### EKS Managed Node Groups (고정 노드)

**장점**:
- AWS가 자동 관리 (패치, 업그레이드)
- 안정적인 온디맨드 인스턴스
- 항상 가용

**단점**:
- 비용 높음
- 유연성 낮음

**FANS에서 사용**:
- General Workers: main-api, scheduler, crawler
- AI Workers: summarize-ai, bias-analysis-ai

#### Karpenter Managed Nodes (동적 노드)

**장점**:
- 필요할 때만 생성 (비용 절감)
- Spot 인스턴스 사용 (70% 절감)
- 초 단위 빠른 스케일링

**단점**:
- Spot 중단 가능성 (드묾)
- 설정 복잡

**FANS에서 사용**:
- AI Worker (큐 처리용): 1~20개 동적 생성

### 2.4 Pod 배치 전략

#### Node Selector (노드 선택)
```yaml
# AI 서비스는 AI Worker 노드에만 배치
nodeSelector:
  workload-type: ai-worker
```

#### Affinity (선호도)
```yaml
# main-api는 각 AZ에 분산 배치 (고가용성)
affinity:
  podAntiAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 100
      podAffinityTerm:
        labelSelector:
          matchExpressions:
          - key: app
            operator: In
            values:
            - main-api
        topologyKey: topology.kubernetes.io/zone
```

#### Taints & Tolerations (격리)
```yaml
# AI Worker 노드는 AI Pod만 배치
taints:
  - key: workload-type
    value: ai-worker
    effect: NoSchedule
```

#### 실제 배치 예시
```
General Worker 노드 (2a):
  ├── main-api Pod 1
  ├── scheduler Pod 1
  └── unified-crawler Pod

General Worker 노드 (2b):
  ├── main-api Pod 2
  └── scheduler Pod 2

AI Worker 노드 (2a):
  ├── summarize-ai Pod 1
  └── bias-analysis-ai Pod 1

AI Worker 노드 (2b):
  ├── summarize-ai Pod 2
  └── bias-analysis-ai Pod 2

Karpenter 노드 (동적):
  └── ai-worker Pod (1~20개)
```

## 3. 네트워크 흐름

### 3.1 사용자 → CloudFront → ALB → EKS

#### 전체 흐름
```
사용자 (www.fans.ai.kr)
  ↓
CloudFront (CDN)
  ↓
Route 53 (DNS)
  ↓
ALB (Public Subnet)
  ↓
Ingress (Kubernetes)
  ↓
Service (ClusterIP)
  ↓
Pod (Private Subnet)
```

#### 단계별 설명

**1단계: 사용자 요청**
```
사용자: https://www.fans.ai.kr 접속
```

**2단계: Route 53 (DNS)**
- **역할**: 도메인을 IP로 변환
- **파일**: `D:\dev1\environments\eks\terraform\route53.tf`
```hcl
# www.fans.ai.kr → CloudFront
resource "aws_route53_record" "www" {
  name = "www.fans.ai.kr"
  type = "A"

  alias {
    name    = aws_cloudfront_distribution.static_assets.domain_name
    zone_id = aws_cloudfront_distribution.static_assets.hosted_zone_id
  }
}
```

**3단계: CloudFront (CDN)**
- **역할**: 정적 파일 캐싱 (React 빌드 파일)
- **파일**: `D:\dev1\environments\eks\terraform\cloudfront.tf`
- **동작**:
  - `/frontend/*` → S3에서 React 앱 제공
  - `/profiles/*` → S3에서 프로필 이미지 제공
  - 404/403 → `/frontend/index.html` (SPA Routing)

**4단계: ALB (Application Load Balancer)**
- **역할**: API 요청을 EKS로 라우팅
- **파일**: `D:\dev1\environments\eks\terraform\alb.tf`
```hcl
# HTTPS Listener
resource "aws_lb_listener" "https" {
  port              = "443"
  protocol          = "HTTPS"
  certificate_arn   = aws_acm_certificate_validation.main.certificate_arn

  # 기본: 프론트엔드
  default_action {
    type             = "forward"
    target_group_arn = aws_lb_target_group.frontend.arn
  }
}

# /api/* → API 타겟 그룹
resource "aws_lb_listener_rule" "api" {
  priority = 100

  condition {
    path_pattern {
      values = ["/api/*"]
    }
  }

  action {
    type             = "forward"
    target_group_arn = aws_lb_target_group.api.arn
  }
}
```

**5단계: Ingress (Kubernetes)**
- **역할**: ALB와 Kubernetes Service 연결
- **파일**: `D:\dev1\environments\eks\manifests\10-ingress.yaml`
```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: fans-ingress
  annotations:
    # ALB 자동 생성
    kubernetes.io/ingress.class: alb
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip

    # SSL 인증서
    alb.ingress.kubernetes.io/certificate-arn: arn:aws:acm:...
    alb.ingress.kubernetes.io/ssl-redirect: '443'
spec:
  rules:
  - host: www.fans.ai.kr
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: main-api-service
            port:
              number: 3000
```

**6단계: Service → Pod**
```yaml
apiVersion: v1
kind: Service
metadata:
  name: main-api-service
spec:
  selector:
    app: main-api
  ports:
  - port: 3000
    targetPort: 3000
  type: ClusterIP
```

#### 실제 예시
```
사용자: GET https://www.fans.ai.kr/api/articles
  ↓
CloudFront: API 요청은 캐시 안 함, 통과
  ↓
ALB: /api/* 규칙 → API 타겟 그룹
  ↓
Ingress: main-api-service:3000
  ↓
Service: Pod IP로 라우팅 (10.0.1.50:3000)
  ↓
Pod: main-api 컨테이너 처리
```

### 3.2 Pod 간 통신

#### Kubernetes DNS
- **자동 생성**: Service 이름으로 통신 가능
- **형식**: `{service-name}.{namespace}.svc.cluster.local`

#### 실제 예시
```javascript
// main-api Pod → summarize-ai Pod 호출
const response = await axios.post(
  'http://summarize-ai-service:8000/api/summarize',
  { text: newsContent }
);
```

#### 내부 통신 흐름
```
main-api Pod (10.0.1.50)
  ↓
Kubernetes DNS: summarize-ai-service → 10.0.1.100
  ↓
summarize-ai Pod (10.0.1.100:8000)
```

#### ConfigMap 설정
- **파일**: `D:\dev1\environments\eks\manifests\03-configmap.yaml`
```yaml
data:
  SUMMARIZE_AI_URL: http://summarize-ai-service:8000
  BIAS_ANALYSIS_AI_URL: http://bias-analysis-ai-service:8002
```

### 3.3 외부 서비스 연결 (RDS, ElastiCache)

#### RDS PostgreSQL 연결

**네트워크 경로**:

## 5. 오토스케일링

### 5.1 KEDA (Pod 레벨 스케일링)

#### 왜 필요한가?
- Redis 큐에 작업이 쌓이면 자동으로 Pod 증가
- 작업 없으면 자동으로 Pod 감소 (비용 절감)
- 비유: 식당에 손님 많으면 직원 증원, 적으면 감원

#### 어떻게 작동하는가?
```
Redis 큐 길이 모니터링
  ↓
큐 길이 > 5 → Pod 추가
  ↓
큐 길이 = 0 → 5분 대기 → Pod 축소
```

#### 어떤 파일에 설정되어 있는가?
- **파일**: `D:\dev1\environments\eks\manifests\16-keda-scaledobject.yaml`

#### 핵심 설정
```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: ai-worker-scaler
  namespace: fans
spec:
  scaleTargetRef:
    name: ai-worker  # 스케일링할 Deployment

  # 범위
  minReplicaCount: 1   # 최소 1개
  maxReplicaCount: 20  # 최대 20개

  # 스케일 다운 정책
  cooldownPeriod: 300  # 5분 대기
  pollingInterval: 30  # 30초마다 확인

  # 트리거: Redis 큐
  triggers:
  - type: redis
    metadata:
      address: redis.fans.svc.cluster.local:6379
      listName: bull:ai-summary:wait  # BullMQ 큐
      listLength: "5"  # 5개당 Pod 1개
      activationListLength: "1"  # 1개 이상이면 활성화
```

#### 실제 스케일링 예시

| 큐 길이 | Pod 개수 | 설명 |
|---------|----------|------|
| 0 | 1 | 최소값 유지 |
| 1~4 | 1 | 아직 활성화 안 됨 |
| 5~9 | 2 | 5개당 1개 규칙 |
| 10~14 | 3 | 계속 증가 |
| 50~54 | 11 | 병렬 처리 |
| 100 | 20 | 최대값 도달 |

#### 시나리오
```
08:00 - 큐: 0개, Pod: 1개 (대기)
10:00 - Crawler가 뉴스 100개 수집
10:10 - Scheduler가 큐에 100개 작업 추가
10:10 - KEDA가 감지: 큐 100개
10:11 - Pod 20개로 스케일 업
10:11~10:15 - 병렬 처리 (5분)
10:15 - 큐: 0개
10:20 - 5분 대기 후 Pod 1개로 축소
```

#### 비용 절감 효과
```
기존 (20개 상시):
  20 Pod × 24시간 × 30일 = 14,400 Pod-시간

KEDA (필요 시만):
  피크 시간 (4시간): 20 Pod × 4 = 80
  일반 시간 (20시간): 1 Pod × 20 = 20
  총: 100 Pod-시간/일 × 30일 = 3,000 Pod-시간

절감률: (14,400 - 3,000) / 14,400 = 79%
```

### 5.2 Karpenter (노드 레벨 스케일링)

#### 왜 필요한가?
- KEDA가 Pod를 늘려도 노드가 부족하면 Pod가 Pending 상태
- Karpenter가 자동으로 EC2 인스턴스 추가
- 비유: KEDA = 직원 채용, Karpenter = 사무실 확장

#### 어떻게 작동하는가?
```
KEDA가 Pod 20개로 증가 요청
  ↓
노드 용량 부족 (Pod Pending)
  ↓
Karpenter가 감지
  ↓
1~2분 내 EC2 인스턴스 생성
  ↓
Pod 자동 배치
```

#### NodePool 종류

**1. General NodePool**
- **용도**: 일반 서비스 (main-api, scheduler)
- **인스턴스**: On-Demand (안정성 중요)
- **타입**: t3.medium, t3.large
- **파일**: `D:\dev1\environments\eks\karpenter\nodepool-general.yaml`

```yaml
apiVersion: karpenter.sh/v1beta1
kind: NodePool
metadata:
  name: general
spec:
  template:
    spec:
      requirements:
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["on-demand"]  # 온디맨드만
        - key: node.kubernetes.io/instance-type
          operator: In
          values: ["t3.medium", "t3a.medium", "t3.large"]

  limits:
    cpu: "8"
    memory: 16Gi

  disruption:
    consolidationPolicy: WhenUnderutilized
    expireAfter: 720h  # 30일
```

**2. AI Worker NodePool**
- **용도**: AI 작업 처리
- **인스턴스**: Spot (비용 절감)
- **타입**: c5.xlarge, c6i.xlarge (CPU 최적화)
- **파일**: `D:\dev1\environments\eks\karpenter\nodepool-ai-worker.yaml`

```yaml
apiVersion: karpenter.sh/v1beta1
kind: NodePool
metadata:
  name: ai-worker
spec:
  template:
    spec:
      requirements:
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["spot"]  # Spot 인스턴스
        - key: node.kubernetes.io/instance-type
          operator: In
          values:
            - c5.xlarge     # 4 vCPU, 8GB
            - c5a.xlarge    # AMD (저렴)
            - c6i.xlarge    # 최신 세대

      # Taints: AI Worker Pod만 배치
      taints:
        - key: workload-type
          value: ai-worker
          effect: NoSchedule

  limits:
    cpu: "16"
    memory: 32Gi

  disruption:
    expireAfter: 168h  # 7일 (Spot은 짧게)
    budgets:
      - nodes: "50%"  # 동시 50%까지 교체 가능
```

### 6.4 인증서 (ACM)

#### SSL/TLS 인증서
- **도메인**: fans.ai.kr, *.fans.ai.kr
- **유효 기간**: 자동 갱신
- **검증 방법**: DNS (Route 53)

#### 파일
- **파일**: `D:\dev1\environments\eks\terraform\acm.tf`

```hcl
resource "aws_acm_certificate" "main" {
  domain_name               = "fans.ai.kr"
  subject_alternative_names = ["www.fans.ai.kr", "*.fans.ai.kr"]
  validation_method         = "DNS"
}

# DNS 검증 레코드 자동 생성
resource "aws_route53_record" "cert_validation" {
  for_each = {
    for dvo in aws_acm_certificate.main.domain_validation_options :
      dvo.domain_name => {
        name   = dvo.resource_record_name
        record = dvo.resource_record_value
        type   = dvo.resource_record_type
      }
  }

  name    = each.value.name
  records = [each.value.record]
  type    = each.value.type
  zone_id = data.aws_route53_zone.main.zone_id
}
```

#### 사용 위치
1. **ALB HTTPS Listener**
```hcl
resource "aws_lb_listener" "https" {

  ssl_policy        = "ELBSecurityPolicy-TLS13-1-2-2021-06"
}
```

## 8. 배포 프로세스

### 8.1 GitHub Actions 워크플로우

#### 전체 워크플로우
```
코드 푸시 (main 브랜치)
  ↓
GitHub Actions 트리거
  ↓
Docker 이미지 빌드
  ↓
ECR 푸시
  ↓
kubectl apply
  ↓
Rolling Update
```

#### 파일
- **파일**: `D:\dev1\.github\workflows\deploy-eks.yml`

#### 주요 단계

**1. 코드 체크아웃**
```yaml
- name: Checkout code
  uses: actions/checkout@v3
```

**2. AWS 인증**
```yaml
- name: Configure AWS credentials
  uses: aws-actions/configure-aws-credentials@v2
  with:
    aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}
    aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
    aws-region: ap-northeast-2
```

**3. ECR 로그인**
```yaml
- name: Login to Amazon ECR
  uses: aws-actions/amazon-ecr-login@v1
```

**4. 이미지 태그 생성**
```yaml
- name: Set image tag
  run: |
    echo "TAG=$(echo $GITHUB_SHA | cut -c1-7)" >> $GITHUB_OUTPUT
    # 예: TAG=a1b2c3d
```

**5. Docker 빌드 및 푸시**
```yaml
- name: Build and push Main API
  run: |
    docker build \
      -t 907123164281.dkr.ecr.ap-northeast-2.amazonaws.com/fans/main-api:${{ steps.image-tag.outputs.TAG }} \
      -t 907123164281.dkr.ecr.ap-northeast-2.amazonaws.com/fans/main-api:latest \
      -f backend/api/Dockerfile \
      backend/api

    docker push 907123164281.dkr.ecr.ap-northeast-2.amazonaws.com/fans/main-api:${{ steps.image-tag.outputs.TAG }}
    docker push 907123164281.dkr.ecr.ap-northeast-2.amazonaws.com/fans/main-api:latest
```

**6. kubectl 설정**
```yaml
- name: Configure kubectl
  run: |
    aws eks update-kubeconfig --region ap-northeast-2 --name fans-cluster
```

**7. Deployment 업데이트**
```yaml
- name: Update image tags
  run: |
    kubectl set image deployment/main-api \
      main-api=907123164281.dkr.ecr.ap-northeast-2.amazonaws.com/fans/main-api:${{ steps.image-tag.outputs.TAG }} \
      -n fans
```

**8. 롤링 업데이트 확인**
```yaml
- name: Verify deployment
  run: |
    kubectl rollout status deployment/main-api -n fans --timeout=5m
```
